Данный сервис получает на вход мероприятия, которые пользователь может получать(GET), создавать(POST), обновлять(PUT) и удалять(DELETE), и выводить информацию в виде HTTP-ответов с телом ответа.

Всего реализовано 10 методов:
1. Получить все мероприятия (HTTP GET /Events)
2. Получить мероприятие по его ID (HTTP GET /Events/{id})
3. Создать мероприятие по телу запроса (HTTP POST /Events)
4. Обновить мероприятие в теле запроса по ID (HTTP PUT /Events/{id})
5. Удалить мероприятие по ID (HTTP DELETE /Events/{id})
6. Получить топ-10 событий (HTTP GET /Events/top)
7. Создать бронь конкретного мероприятия по ID (HTTP POST /Bookings/{id}/book)
8. Получить бронь по его ID (HTTP GET /Bookings/{id})
9. Отменить бронь по его ID (HTTP DELETE /Bookings/{id})
10. Регистрировать нового пользователя по телу запроса (HTTP POST /Auth/register)
11. Логин пользователя по телу запроса (HTTP POST /Auth/login)

## Структура проекта и назначение каждого слоя
Структура Приложения на ASP.NET Core создана согласно принципам чистой архитектуры (_Clean Architecture_), где каждый файл, отвечающий за свою роль (интерфейс, реализация, репозиторий, Доменная сущность и т.д), находится в определенном слое приложения для разделения на собственные задачи.

Данная структура разделена на 3 отдельных микросервиса Events, Bookings и Users, где каждый микросервис ничего не знает друг о друге и обмен происходит событиями через брокер сообщений Kafka с топиком booking-confirmed. В корне проекта находится docker-compose файл, содержащий 3 БД под каждый микросервис(database per service) со своими портами общения(Events имеет порт 5434, Bookings - 5435, Users - 5433), а также имеет Kafka  с портом 9092, через который общаются микросервисы.

Таблица
**Таблица «сервис — БД — порт»:**

| Сервис | БД (контейнер) | Порт БД (хост) | Swagger |
| :--- | :--- | :--- | :--- |
| `UserService` | `users-db` (`users`) | `5433` | `https://localhost:7283/swagger` |
| `EventService` | `events-db` (`events`) | `5434` | `https://localhost:7284/swagger` |
| `BookingService` | `bookings-db` (`bookings`) | `5435` | `https://localhost:7285/swagger` |
| Kafka | `kafka` + `zookeeper` | `9092` | — |

Есть топик BookingConfirmed, к которому обращаются сервисы Events и Bookings с каждой своей ролью(продюсером-публикатором или консьюмером-подписчиком события).

Bookings участвует в роли продюсера, который создает бронь и после сохранения данных в соей БД отправляет событие в топик BookingConfirmed с такими данными: Id брони, Id на мероприятие, Id пользователя, количеством мест и временем подтверждения отправки в брокер Kafka.

Events участвует в роли консьюмера-подписчика на принятие события из брокера Kafka по pull-модели, где сам консьмер берет событие из брокера а не брокер сам дает событие. Данный консьюмер берет событие из Kafka и в зависимости от своей логики и соыбтия определяет, что делать с данным событием(занять место на мероприятие и передать событие обратно в Kafka, что данное событие обработано)  

Данные принципы чистой архитектуры позволяют правильно делать отношение слоев друг с другом, чтобы не впутывать логику в другие слои.

## Ролевая модель и разграничение прав
В приложении реализована модель User с ролями "User" и "Admin" со своими правами на отправку HTTP-запросов. Некоторые методы не требует авторизации пользователя, что дает дает доступ для таких действий как:
1. Получить список всех событий с возможностью фильтрации
2. Получить определенное событие по его Id

Для возможности бронировать события на мероприятие необходимо авторизоваться под ролью User или Admin (но, есть ограничение на 10 активных броней)

Роль User может:
1. Создать бронь на определенное событие, но только тогда, когда событие еще не прошло
2. Отменить бронь на событие, которое он сам бронировал, другой пользователь с ролью User не может это сделать

Роль Admin может:
1. Создать бронь на определенное событие, но только тогда, когда событие еще не прошло
2. Отменить бронь на событие, которое он сам бронировал и бронировал другой пользователь с любой ролью User или Admin
3. Создать новое событие
4. Изменить событие
5. Удалить событие

Для возможности выполнять задачи согласно своей роли необходимо сделать такие шаги:

## Инвалидация кеша и обоснование стратегии
В микросервисе Events реализовано кеширование Redis в методах контроллерах: **Получить топ-10 событий(HTTP GET /Events/top)** и **Получить мероприятие по его ID (HTTP GET /Events/{id})**. 

1. При первой попытке получить **топ-10 событий**, в первую очередь обращается к БД, чтобы получить данные исходя из процента продаж на определенное событие. После получения данных из БД "прогреваем" кеш и при последующих запросах можно моментально получить значения из кеша Redis.
2. при первой попытке получить событие по его Id, в первую очередь обращается к БД, чтобы получить событие по ID. После получения данных из БД "прогреваем" кеш и при последующих запросах можно моментально получить значения из кеша Redis.

Однако возникает ситуация, когда после изменения данных события, изменения неправильно отображаются пользователю, т.к. при запросе обращаемся не к новым данным, а к устаревшим из кеша. Дабы решить такую ситуацию, можно применить компромисы и решения данной проблемы для определенных запросов. Для каждого запроса некритичны устаревшие данные в определенный промежуток времени, а где-то необходимо учесть критичность использования устареших данных.

Решение для запроса **Получить топ-10 событий(HTTP GET /Events/top)**:
1. Для данного запроса некритично использование устаревших данных, но нужно заложить время жизни кеша(TTL), чтобы спустя день или больше не показывались старые данные. В данном запросе время жизни заложено в 5 минут

Решение для запроса **Получить мероприятие по его ID (HTTP GET /Events/{id})**:
1.  В данном запросе будет критично использование устаревших данных, т.к. при изменении данных о событии (название, время события), будет непонятно пользователю, на что он мог забронировать. Хоть TTL задан в 30 минут, надо очистить кеш при удалении **(HTTP DELETE /Events/{id})** или изменении **(HTTP PUT /Events/{id})**. После очищения кеша, первый запрос снова обратится к БД и только потом снова запишет в кеш новые значения.

## Установка и запуск контейнера docker
Данный контейнер(docker-compose_14.yml) лежит в корне решения, рядом с EventTicketBookingService.slnx. Он необходим для поднятия БД внутри контейнера и прослушивания портов данного БД, порты захватывает appsettings.json**.

Чтобы запустить данный контейнер, надо перейти в папку, в которой лежит данный файл и запустить команду
```
docker compose -f docker-compose_14.yml up -d
# В случае если не получается связаться с БД через приложение, то можно "снести" и поднять снова
# Предупреждение! Если ввести команду снизу, то все данные с БД будут потеряны, применять в крайнем случае
docker compose -f docker-compose_.yml down -v
```

1. При вызове **GET /Events**. Получаем все мероприятия в формате JSON-объекта(Id, Title, Description, StartAt, EndAt, TotalSeats, AvailableSeats).

Формат модели события
```
{
  "id": 0,
  "title": string,
  "description": string,
  "startAt": DateTime,
  "endAt": DateTime,
  "totalSeats": int,
  "availableSeats": int
}
где
id - целочисленный тип, является идентификатором самого мероприятия и является уникальным
title - строка, является названием мероприятия
description - строка, описание мероприятия
startAt - дата начала мероприятия
endAt - дата окончания мероприятия
totalSeats - целочисленный тип, количество мест на данное мероприятие
availableSeats - целочисленный тип, доступное на данный момент количество мест на данное мероприятие

```

Была добавлена возможность фильтрации по подстроке в Title(регистронезависимый, частичное совпадение), а также по from и to (from  - события, которые начинаются не раньше указанной даты, to - события, которые заканчиваются не позже указанной даты)

В случае если нет никаких мероприятий, то выведется пустое тело в виде 
```
"{
  "totalCount": 0,
  "events": [],
  "pageIndex": 1,
  "pageSizeByIndex": 0
}"
```
(см. 1 скриншот). С внедрением возможности фильтрации и пагинации, данный метод теперь может получать нужные названия и регулировать диапазон времени от начала события и до конца события, а также выводить мероприятия по нужной странице с определенным количеством элементов на странице(см 2 скриншот). Иначе после добавления(POST смотреть во 2 пункте) или изменения(PUT смотреть в 4 пункте) будет отображены JSON-объекты(см. 3 скриншот)

При создании брони, необходимо некоторое время, чтобы получить новый статус и дату, когда обработка прошла успешно. 

Необходимо, чтобы брони, которые могут быть более 1 или 1000, не "забивали" поток и обрабатывались на фоне.

Для этого был реализован фоновый процесс, в который передается бронь в рамках очереди и обрабатывает бронь и переводит его из статуса Pending в статус Confirmed или Rejected.

Имитация операции всего 2 секунды для одной брони.

Сценарий получения статуса брони рассматривается в 7 пункте по **GET /Bookings/{id}**.

При создании брони для существующего события есть доступные места, которые бронирую пользователи. Однако, когда доступные места закончились и при попытке создать бронь, возвращает ответ 409(Conflict), сигнализируя, что нельзя забронировать место под мероприятие из-за недоступных мест. 

7. При вызове **GET /Bookings/{id}**. Получаем бронь по его ID.
При создании брони согласно 7 пункту с методом **POST /Events/{id}/book**, можно получить его объект модели Booking, формат которого
```
{
  "id": int,
  "eventId": int,
  "status": BookingStatus,
  "createdAt": DateTime,
  "processedAt": DateTime
}
где
id - целочисленный тип, является идентификатором самой брони и является уникальным
eventId - целочисленный тип, является идентификатором самого мероприятия 
status - тип перечисления BookingStatus, принимает 1 из 3 состояний (Pending, Confirmed или Rejected) в числовом формате
createdAt - дата с момента создания брони
processedAt - дата завершения обработки брони
```

В приложении были применены такие примитивы синхронизации:
1. Семафор - асинхронный потокобезопасный примитив. Предназначен для вхождения определенного количества потоков к одному общему ресурсу (В данном сервисе несколько потоков может входить). Данный примитив необходим для того, чтобы при параллельной обработке множества брони, другие потоки не могли изменить общий ресурс.
2. Конкурентные коллекции - использованы ConcurrentDictionary для хранения ID и объекта события, а также ID и объекта брони в формате ключ-значение, ConcurrentQueue для хранения очереди ID задач бронирования. Данные коллекции необходимы для потокобезопасной записи и чтения данных при параллельной работе сервиса, т.к. несколько потоков могут одновременно изменить одно и тоже значение, что чревато непредвиденными изменениями 
3. Lock - синхронный потокобезопасный примитив. Предназначен для вхождения только одного потока в критическую секцию. Данный примитив необходим для того, чтобы при параллельном создании брони другие потоки не могли изменить общий ресурс.

### Команды для создания и применения миграций
```
// Создание миграции, где потом в приложении создается папка Migrations со снапшотом и датой и названием миграции(Например InitialCreate)
// делать надо в корне проекта рядом с солюшен EventTicketBookingService.slnx
dotnet ef migrations add *Имя* --project Events/EventService.Infrastructure/EventService.Infrastructure.csproj --startup-project Events/EventService.Presentation/
dotnet ef migrations add *Имя* --project Bookings/BookingService.Infrastructure/BookingService.Infrastructure.csproj --startup-project Bookingss/BookingService.Presentation/
dotnet ef migrations add *Имя* --project Users/UserService.Infrastructure/UserService.Infrastructure.csproj --startup-project Users/UserService.Presentation/
// Применение миграции,
// При её вызове EF Core:
// 1. Подключается к базе данных;
// 2. Проверяет таблицу __EFMigrationsHistory, где хранится история применённых миграций, и определяет, какие из них уже были выполнены;
// 3. Выполняет недостающие.
dotnet ef database update /*Именование миграции*/ --project EventTicketBookingService.Infrastructure --startup-project EventTicketBookingService
```
