# Разработка сервиса бронирования билетов на мероприятие

Зависимости:
- Visual Studio 2026
- .NET 10
- ASP.NET Core MVC
- EF Core
- Swagger
- Docker Desktop
- Postgres

Данный сервис получает на вход мероприятия, которые пользователь может получать(GET), создавать(POST), обновлять(PUT) и удалять(DELETE), и выводить информацию в виде HTTP-ответов с телом ответа.

Всего реализовано 7 методов:
1. Получить все мероприятия (HTTP GET /Events)
2. Получить мероприятие по его ID (HTTP GET /Events/{id})
3. Создать мероприятие по телу запроса (HTTP POST /Events)
4. Обновить мероприятие в теле запроса по ID (HTTP PUT /Events/{id})
5. Удалить мероприятие по ID (HTTP DELETE /Events/{id})
6. Создать бронь конкретного мероприятия по ID (HTTP POST /Events/{id}/book)
7. Получить бронь по его ID (HTTP GET /Bookings/{id})

## Установка и запуск контейнера docker
Данный контейнер(docker-compose_.yml) лежит в папке проекта EventTicketBookingService. Он необходим для поднятия БД внутри контейнера и прослушивания портов данного БД, порты настраиваются в **переменных окружениях и захватывает appsettings.json**.

В docker-файле есть переменные 
```
${POSTGRES_USER} - имя пользователя БД,
${POSTGRES_PASSWORD} - Пароль к БД,
${POSTGRES_DB} - название БД
```

Чтобы их задать надо ввести значения в командной строке (Примечание: введя данные, значения сохранятся в контейнере, но если сделать docker compose -f docker-compose_.eml down -v, то данные сотрутся и может произойти ошибка подключения к БД при повторном запуске)

Пример ввода данных в командной строке (должны вводиться данные в папке где находится docker-compose_.yml):
```
PowerShell(Windows)
$env:POSTGRES_USER="postgres"
$env:POSTGRES_PASSWORD="postgres"
$env:POSTGRES_DB="eventapi"
```

Чтобы запустить данный контейнер, надо перейти в папку, в которой лежит данный файл и запустить команду
```
docker compose -f docker-compose_.yml up -d
# В случае если не получается связаться с БД через приложение, то можно "снести" и поднять снова
# Предупреждение! Если ввести команду снизу, то все данные с БД будут потеряны, применять в крайнем случае
docker compose -f docker-compose_.yml down -v
```

## Тест данных методов
В браузере в swagger будут доступны 7 HTTP-методов, выполняющих тесты запросов.
Для выполнения запросов, необходимо выбрать один из методов, отображенных в swagger и нажать Try it out, после Execute для выполнения самого запроса.


1. При вызове **GET /Events**. Получаем все мероприятия в формате JSON-объекта(Id, Title, Description, StartAt, EndAt, TotalSeats, AvailableSeats).

Формат модели события
```
{
  "id": 0,
  "title": string,
  "description": string,
  "startAt": DateTime,
  "endAt": DateTime,
  "totalSeats": int,
  "availableSeats": int
}
где
id - целочисленный тип, является идентификатором самого мероприятия и является уникальным
title - строка, является названием мероприятия
description - строка, описание мероприятия
startAt - дата начала мероприятия
endAt - дата окончания мероприятия
totalSeats - целочисленный тип, количество мест на данное мероприятие
availableSeats - целочисленный тип, доступное на данный момент количество мест на данное мероприятие

```

Была добавлена возможность фильтрации по подстроке в Title(регистронезависимый, частичное совпадение), а также по from и to (from  - события, которые начинаются не раньше указанной даты, to - события, которые заканчиваются не позже указанной даты)

В случае если нет никаких мероприятий, то выведется пустое тело в виде 
```
"{
  "totalCount": 0,
  "events": [],
  "pageIndex": 1,
  "pageSizeByIndex": 0
}"
```
(см. 1 скриншот). С внедрением возможности фильтрации и пагинации, данный метод теперь может получать нужные названия и регулировать диапазон времени от начала события и до конца события, а также выводить мероприятия по нужной странице с определенным количеством элементов на странице(см 2 скриншот). Иначе после добавления(POST смотреть во 2 пункте) или изменения(PUT смотреть в 4 пункте) будет отображены JSON-объекты(см. 3 скриншот)

При создании брони, необходимо некоторое время, чтобы получить новый статус и дату, когда обработка прошла успешно. 

Необходимо, чтобы брони, которые могут быть более 1 или 1000, не "забивали" поток и обрабатывались на фоне.

Для этого был реализован фоновый процесс, в который передается бронь в рамках очереди и обрабатывает бронь и переводит его из статуса Pending в статус Confirmed или Rejected.

Имитация операции всего 2 секунды для одной брони.

Сценарий получения статуса брони рассматривается в 7 пункте по **GET /Bookings/{id}**.

При создании брони для существующего события есть доступные места, которые бронирую пользователи. Однако, когда доступные места закончились и при попытке создать бронь, возвращает ответ 409(Conflict), сигнализируя, что нельзя забронировать место под мероприятие из-за недоступных мест.

```

  "eventId": int,
  "status": BookingStatus,
  "createdAt": DateTime,
  "processedAt": DateTime
}
где

eventId - целочисленный тип, является идентификатором самого мероприятия

```

В приложении были применены такие примитивы синхронизации:
1. Семафор - асинхронный потокобезопасный примитив. Предназначен для вхождения определенного количества потоков к одному общему ресурсу (В данном сервисе несколько потоков может входить). Данный примитив необходим для того, чтобы при параллельной обработке множества брони, другие потоки не могли изменить общий ресурс.
2. Конкурентные коллекции - использованы ConcurrentDictionary для хранения ID и объекта события, а также ID и объекта брони в формате ключ-значение, ConcurrentQueue для хранения очереди ID задач бронирования. Данные коллекции необходимы для потокобезопасной записи и чтения данных при параллельной работе сервиса, т.к. несколько потоков могут одновременно изменить одно и тоже значение, что чревато непредвиденными изменениями 
3. Lock - синхронный потокобезопасный примитив. Предназначен для вхождения только одного потока в критическую секцию. Данный примитив необходим для того, чтобы при параллельном создании брони другие потоки не могли изменить общий ресурс.

### Команды для создания и применения миграций
```
// Создание миграции, где потом в приложении создается папка Migrations со снапшотом и датой и названием миграции(Например InitialCreate)
// делать надо в корне проекта рядом  солюшен EventTicketBookingService.slnx
dotnet ef migrations add *Имя* --project EventTicketBookingService.Infrastructure --startup-project EventTicketBookingService
// Применение миграции,
// При её вызове EF Core:
// 1. Подключается к базе данных;
// 2. Проверяет таблицу __EFMigrationsHistory, где хранится история применённых миграций, и определяет, какие из них уже были выполнены;
// 3. Выполняет недостающие.
dotnet ef database update /*Именование миграции*/ --project EventTicketBookingService.Infrastructure --startup-project EventTicketBookingService
```
